# Lote FX03 (front): correcciones de la verificación final

Contexto: los 39 puntos del review de Catálogos E2 (docs/reviews/2026-10-23-code-review-catalogos-e2.md del back) ya están implementados. Tres verificaciones de solo lectura y las revisiones finales de cada lote dejaron los hallazgos de abajo. Este lote corrige los de su área. El pedido del usuario de cada punto está en los briefs Fxx.md y Bxx.md de esta carpeta (F49.md trae 35 a 39). Las reglas de interfaz están en docs/design/visual-baseline.md del front («Pantalla» y «Formularios y diálogos») y el contrato de mensajes en docs/guides/mensajes-y-estados.md.

Cómo trabajar cada hallazgo: verificalo primero en el código actual (pudo cambiar después de que se escribió). Si no es real, no cambies nada y explicalo. Si es real, regresión en rojo primero cuando es comportamiento, después el arreglo, y un commit chico por hallazgo o por grupo de hallazgos repetidos. Si un hallazgo cambia lo que muestra una prueba visual (src/test/visual), actualizá su spec; las capturas se regeneran al cierre. Si cambia una regla o una guía, actualizala en el mismo commit.

## Decisiones ya tomadas para este lote

- A8 y A10 son el mismo problema: «Volver a cargar el dato» muestra la carga y el error si la relectura falla.
- V9 y V23 son el mismo problema.
- RF13-1: durante la espera de un 429, ninguna consulta reintenta sola (ni al volver el foco a la ventana ni al reconectar).
- V28: el diálogo de un dato de las personas valida al intentar guardar y, después del primer error, en vivo; Guardar no se apaga por campos vacíos.

## Hallazgos

### Hallazgo A8 — punto 26 (minor, fv3/completitud)

Dónde: ArquitecturaBaseFront/src/features/business-forms/components/PersonAttributeDialog.tsx:34 y :63; src/features/business-forms/pages/PersonDataPage.tsx:57; src/features/business-forms/hooks/usePersonData.ts:15

Problema: «Volver a cargar el dato» no tiene estado de carga ni de error. Si la relectura falla, no se avisa nada y el foco pasa a Nombre como si se hubiera recargado, aunque el conflicto sigue y Guardar sigue deshabilitado.

Evidencia: `reload = () => void onReload().then(() => nameRef.current?.focus())` no marca la espera, y el botón solo se deshabilita con `busy`, que la recarga no prende. `reloadEditing` hace `await attributes.refetch()`, que no lanza: ante un 500 o un error de red, `result.data` sigue siendo la lista en caché y `find` devuelve el mismo objeto que `editing`. Entonces `attribute !== loaded` da falso y el diálogo queda igual. El query de atributos tiene `meta: { errorOwner: "local" }`, y el QueryCache global no avisa los errores con ese `errorOwner` (queryClient.ts:12). La página tampoco muestra el error porque sigue teniendo `attributes.data`. Los errores de red se reintentan dos veces, así que pasan unos segundos sin indicación y la falla queda en silencio. visual-baseline pide que «los cambios asincrónicos importantes se anuncian».

Arreglo propuesto: Que `onReload` devuelva si la relectura salió bien (`!result.isError`). En el diálogo, un estado `reloading` deshabilita el botón mientras relee. Si falla, se muestra `readErrorMessage(result.error)` en el `role="alert"` existente y no se mueve el foco a Nombre. Sumar un caso a PersonDataPage.test con el GET de atributos respondiendo 500 después del 409.


### Hallazgo A10 — punto 26 (minor, fv3/correccion)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\pages\PersonDataPage.tsx:57 (and PersonAttributeDialog.tsx:34)

Problema: If the refetch fails, «Volver a cargar el dato» does nothing and shows nothing. reloadEditing never checks result.isError. On a failed refetch (network error or 5xx), TanStack keeps the previous data, so find() returns the same snapshot object that is already in `editing`. setEditing then changes nothing and the dialog does not reset. The attributes query uses meta.errorOwner "local", so no global toast appears. The page only shows the error when `attributes.error && !attributes.data`, and data is still there. The user is left with the same 409 alert and Guardar disabled, with no sign that the reload failed.

Evidencia: PersonDataPage.tsx:57: `const reloadEditing = async () => { const result = await attributes.refetch(); setEditing(current => current && current !== "new" ? result.data?.items.find(item => item.id === current.id) ?? null : current); };` has no check of result.isError or result.error. usePersonData.ts:15 declares the attributes query with `meta: { errorOwner: "local" }`. PersonDataPage.tsx:61 only renders the error when `attributes.error && !attributes.data`. PersonAttributeDialog.tsx:34: `const reload = () => void onReload().then(() => nameRef.current?.focus());` does not learn whether the reload worked. By contrast, PersonDataSection still shows readErrorMessage(data.error) when its reload fails.

Arreglo propuesto: Have onReload return whether it succeeded. In reloadEditing, when the refetch fails, return false (or the error) and do not replace `editing`. The dialog then shows that error in its alert, for example operationalErrorMessage(result.error, t, "load") or readErrorMessage, so «Volver a cargar el dato» stays available for another try. Add a test where the GET of person-attributes fails after the 409.

Arreglo propuesto: Cuando `error.code === "Forms.PersonAttribute.ValueRemovalNotConfirmed"` y `confirmValues` es true, o cuando el tipo y la fuente vuelven a los guardados, omitir ese mensaje en `message("type")` y `message("sourceCatalogId")`. La casilla se sigue mostrando mientras haya un cambio de tipo o fuente pendiente. Agregar al test «asks to confirm clearing stored values…» la verificación de que, con la casilla marcada, Tipo ya no está aria-invalid.


### Hallazgo A11 — punto 28 (minor, fv4/completitud)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\components\CatalogQuestionSettings.tsx:73-74 (with hooks/useRecipientPreview.ts:15-25)

Problema: «Reintentar» is offered for any failure of the test-person list, including errors that cannot be retried (400, 401, 403). The P28 rule, which the preview and the maximum follow through isRetryable, retries only network errors, 5xx and 429. A 403 on the list also does not show the «sin permiso» state («Ya no tenés permiso para probar con personas.»): it shows the generic failure with an enabled button that fails again on every click.

Evidencia: `const offerRetry = samples.isError || preview.canRetry || preview.waitSeconds > 0` and `const retryDisabled = samples.isError ? retryWait > 0 : !preview.canRetry`: whenever samples.isError is true, the button is offered and stays enabled once the 429 wait ends, whatever the status was. useRecipientSamples (useRecipientPreview.ts:21-25) only handles 429 (restart of the countdown) and exposes no flag saying whether the error can be retried. Example: Autocomplete.tsx sets no maxLength and PagedRequestValidator limits Search to 100 (PagedRequest.MaxSearchLength). Typing 101 characters in «Como si lo recibiera» gets a 400 from GET recipient-samples. The screen shows «No se pudo preparar la vista previa.» with «Reintentar» enabled, and the retry repeats the same 400. The same happens with a 403 if the permission is taken away mid-session. The regressions only cover a 500 («retries the recipient samples after they fail») and a 429.

Arreglo propuesto: Have useRecipientSamples expose `canRetry` with the same isRetryable (network/5xx/429) and without a running cooldown. In CatalogQuestionSettings, offer the button only when `samples.isError && isRetryable(samples.error)`. Treat a 401/403 from the list like the preview's denied state. Add a regression with a 403 or 400 from recipient-samples that does not offer «Reintentar».


### Hallazgo A12 — punto 32 (minor, fv4/correccion)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\hooks\useRecipientPreview.ts:75 (called from components\CatalogQuestionSettings.tsx:55)

Problema: CE4-A: the editor's maximum («Como mucho N por persona» / «Todos ven las mismas N») is not reread when the catalog's revision changes. The hook's stamp only carries the scope, the catalog id, the filters and the attempt. If the catalog changes while the question editor is open (edited in another tab, or an import), the detail refetches with a new revision, but the line keeps the old N and the old fit verdict until the author changes a filter or reloads the page.

Evidencia: useRecipientPreview.ts:75: `const stamp = canPreview(scope) && complete ? JSON.stringify([formScopeKey(scope), normalizeCatalogQuestionSource({ catalog, match }), attempt]) : null;` contains no revision. In the same component, the reads that do depend on the catalog are keyed by revision: useCatalogItems(..., catalog?.revision ...) at CatalogQuestionSettings.tsx:48, and useCatalogPresentationCheck(..., catalog?.revision ?? null, ...) at :71 (root `[..., "presentation-check", id, revision]` in useCatalogQueries.ts:28). useCatalogDetail (useCatalogQueries.ts:14) uses staleTime 0, so it refetches on window focus and brings the new revision, but the maximum is not reread. The hooks AGENTS.md documents the stamp as «dueño, catálogo y filtros», which also leaves out the revision.

Arreglo propuesto: Pass the catalog revision to useRecipientMaximum (for example `useRecipientMaximum(scope, catalog?.kind === "Manual" ? source : null, catalog?.revision ?? null)`) and include it in the stamp, as the presentation check and the items read already do. Add a test that changing the revision triggers a new read after 300 ms, and update the line in hooks/AGENTS.md.


### Pendiente de la revisión final del lote F13 (blocker)

Dónde: ArquitecturaBaseFront src/features/business-forms/hooks/useRecipientPreview.ts:19-22 (the useQuery in useRecipientSamples, 4192f02)

Problema: The fix only disables the button. The samples query still retries automatically inside the server's 429 window. The query keeps TanStack's default refetchOnWindowFocus and refetchOnReconnect, and the app sets no focusManager of its own. I checked query-core 5.103.1: an errored query has no data, so isStaleByTime returns true and Query.onFocus calls observer.refetch(). This query also has staleTime: 0. Example: samples answer 429 with retryAfter 60, the screen shows Reintentar disabled with «Esperá N segundos…», the author switches browser tabs and comes back inside the 60 s, and GET /api/forms/recipient-samples goes out again with no click. That is the same request inside the window that the earlier blocker described, with the trigger moved from a click to the focus event. It breaks point 28 for this route («respeta la espera de un 429»). It breaks mensajes-y-estados.md («no se habilita un reintento prematuro»). It also contradicts components/AGENTS.md, which this commit edited and which says the samples read is repeated «sólo al tocarlo». The existing pattern for a query with a 429 wait avoids this: useFormComposer.ts:45 and :54 set refetchOnWindowFocus: false and refetchOnReconnect: false next to the queryFn catch, and useResponseCount pauses the query. The implementer copied the queryFn catch from useResponseCount but not the part that stops automatic refetches. The new regression asserts requests.samples === 1 right after the alert shows, so it does not catch a later automatic retry.

Arreglo propuesto: Add refetchOnWindowFocus: false and refetchOnReconnect: false to the useRecipientSamples query, as useFormComposer does. A failed samples read then repeats only through Reintentar, and only after the wait. Write the regression first, in CatalogQuestionSettings.test.tsx: after the 429 with retryAfter 5, run `await act(async () => { focusManager.setFocused(false); focusManager.setFocused(true); })` (the pattern in FormReplyFiles.test.tsx:28). Then assert that requests.samples is still 1 and Reintentar is still disabled. Restore focusManager.setFocused(undefined) when the test ends. If you want, mention in hooks/AGENTS.md that the samples do not refetch on focus or reconnect.
