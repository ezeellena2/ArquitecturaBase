# Lote FX02 (front): correcciones de la verificación final

Contexto: los 39 puntos del review de Catálogos E2 (docs/reviews/2026-10-23-code-review-catalogos-e2.md del back) ya están implementados. Tres verificaciones de solo lectura y las revisiones finales de cada lote dejaron los hallazgos de abajo. Este lote corrige los de su área. El pedido del usuario de cada punto está en los briefs Fxx.md y Bxx.md de esta carpeta (F49.md trae 35 a 39). Las reglas de interfaz están en docs/design/visual-baseline.md del front («Pantalla» y «Formularios y diálogos») y el contrato de mensajes en docs/guides/mensajes-y-estados.md.

Cómo trabajar cada hallazgo: verificalo primero en el código actual (pudo cambiar después de que se escribió). Si no es real, no cambies nada y explicalo. Si es real, regresión en rojo primero cuando es comportamiento, después el arreglo, y un commit chico por hallazgo o por grupo de hallazgos repetidos. Si un hallazgo cambia lo que muestra una prueba visual (src/test/visual), actualizá su spec; las capturas se regeneran al cierre. Si cambia una regla o una guía, actualizala en el mismo commit.

## Decisiones ya tomadas para este lote

- A6 y A19 son el mismo problema: el guard de `uses` no tiene tope, porque el contrato del back no lo tiene.
- V4 y V5 son el mismo problema: «Generar código» usa el texto en el idioma del menú y, si falta, el original del catálogo.
- A15: «Zonas · N opciones» cuenta solo las opciones activas, las que se pueden elegir. Si el back no da ese número, usá el que muestra el listado de catálogos.
- A18: el respaldo local del chequeo de presentación, con cambios sin guardar, se calcula en cada idioma que tenga el catálogo, con títulos de 30 y descripciones de 300, sobre lo que está cargado.

### Hallazgo A6 — punto 2 (minor, fv1/correccion)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\api\catalogFieldFeedback.ts:11

Problema: The 409 FieldInUse guard is stricter than the contract: it accepts at most 100 `uses`, but the back does not cap them. With more than 100, the whole feedback is discarded and the uses list (and «Ir a la pregunta») disappears without any notice.

Evidencia: Front: `uses: z.array(catalogFieldUsageSchema).max(100).optional()`. ### Hallazgo A19 — punto 11 (minor, fv6/correccion)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\api\catalogFieldFeedback.ts:11

Problema: The zod guard for the `uses` of a FieldInUse 409 accepts at most 100 entries, but the back puts no limit on them. When a field has more than 100 uses, `readCatalogFieldFeedback` returns null for the whole response. The 409 then shows only the error message next to the field: «En uso» loses its list. A reader without formtemplates.read also loses the count by stage, which point 11 asks to keep («sin él, el bloqueo y la cantidad»). The same uses in the catalog detail (`usedBy`, catalogResponse.ts:24) have no limit, so the two guards disagree.

Evidencia: Front: `uses: z.array(catalogFieldUsageSchema).max(100).optional()` sits inside a strictObject, and a failed `safeParse` returns null (catalogFieldFeedback.ts:22-23). Back: FormCatalogFieldRecorder.cs:66-67 builds `InUse(FormCatalogFieldUsagePolicy.Describe(usesByField[field.Id], canReadForms), ...)` from every row, and the role, type or source change does the same with `filters` (:61-62). With formtemplates.read, Describe returns one entry per question and stage (FormCatalogFieldUsagePolicy.cs:12); without it, one per form and stage. ProblemDetailsMapper.AddErrorExtensions copies the metadata without trimming it. api/AGENTS.md:42 documents `uses` with no limit. Example: a «Zona» field used as a filter by 51 forms, each in its draft and its active version, produces 102 uses. The list disappears and only «El campo está en uso…» remains.

Arreglo propuesto: Remove the `.max(100)` from `uses` so the guard matches the contract (the detail's `usedBy` has no limit either). If the bound is meant to stay, cap or summarize the uses in the back before they enter the metadata and document that in both repos.


### Hallazgo A15 — punto 32 (minor, fv5/correccion)

Dónde: ArquitecturaBaseFront/src/features/business-forms/components/CatalogFieldSourceSummary.tsx:13 (contra ArquitecturaBase/src/ArquitecturaBase.Infrastructure/Modules/BusinessForms/Persistence/Readers/FormCatalogReader.cs:129)

Problema: El detalle CE1 «Zonas · N opciones» cuenta también las opciones dadas de baja de la fuente. Así no coincide con la cantidad del listado de catálogos ni con las opciones que se pueden elegir en la celda.

Evidencia: CatalogFieldSourceSummary muestra `detail.data.itemsCount`. En el back, `FormCatalogReader.FindAsync` arma ese ItemsCount con `dbContext.Set<BusinessFormCatalogItem>().Count(item => item.CatalogId == value.Id)`, sin filtrar `IsActive` (línea 129). El listado (`optionsCount`, línea 76) cuenta solo `item.IsActive`. La búsqueda de la celda (`CatalogExtraFieldInput.tsx:28`, `isActive: true`) ofrece solo activas. El tablero CE1/CE2 usa el mismo 72 en «Zonas · 72 opciones» y en «Escribí para buscar entre las 72 de «Zonas»». Con una opción dada de baja en Zonas, el campo dice «Zonas · 73 opciones» mientras el listado y el buscador trabajan con 72.

Arreglo propuesto: Contar solo las opciones activas de la fuente. Hay dos caminos: que el detalle devuelva el conteo activo, revisando antes quién más lee `itemsCount`, como el recibo de importación; o que CatalogFieldSourceSummary lea `totalCount` de `useCatalogItems(scope, id, revision, { page: 1, pageSize: 1, isActive: true })`. Sumar un caso con una opción inactiva al test «numbers the active fields and shows each type's detail».


### Hallazgo A18 — punto 23 (minor, fv6/completitud)

Dónde: C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\components\CatalogPresentationSection.tsx:30-34 (wired from C:\Users\ezequ\source\repos\ArquitecturaBaseFront\src\features\business-forms\pages\CatalogEditorPage.tsx:244)

Problema: While the catalog editor has unsaved changes, the per-language check (titles over 30, descriptions over 300) disappears. The fallback counts only titles over 30, in the language on screen, and only among the options loaded on the current page. Any edit, such as changing one option's text, hides a server warning like «En inglés: 2 opciones superan los 300 caracteres de la descripción.» until the next save. Point 23 asks that the check run in every language the catalog has, with descriptions capped at 300.

Evidencia: CatalogEditorPage.tsx:244 passes `check={!editor.dirty ? (editor.confirmed ?? initial)?.presentationCheck : undefined}`. CatalogPresentationSection.tsx:30 has `const localTooLong = check === undefined ? items.filter(item => item.isActive && catalogOptionPresentation(...culture...).title.length > 30).length : 0;`, which never looks at `.description`. :31-34 builds `problems` only from `check?.cultures`, so with `check === undefined` no description or other-language warning is shown. components/AGENTS.md (CE3) documents this fallback as «cuenta las opciones cargadas en el idioma mostrado». No test covers the dirty state with a description over 300.

Arreglo propuesto: The simplest fix: in the `check === undefined` fallback, also count `catalogOptionPresentation(...).description` over 300 in the language on screen and show it with `catalogs.presentation.descriptionTooLongIn`, the same way as titles. Alternatively, keep showing the last confirmed server check while only items change, and fall back to local counting only when the presentation or the fields change. Add a CatalogPresentationSection test with `check` undefined and one option whose description is over 300.
