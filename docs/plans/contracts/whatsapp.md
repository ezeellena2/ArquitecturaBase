# Contratos HTTP de WhatsApp para la migración MVC

Inventario de la Tarea 0 del [plan de migración](../2026-09-23-migracion-mvc-servicios-repositorios.md). Describe el comportamiento actual que deben conservar los controllers. Cada fila representa una combinación de verbo y ruta; las rutas compartidas con correo y perfil se detallan aparte. Los errores de negocio y del framework usan `ProblemDetails` con `code` y `traceId`; las validaciones agregan `errors` y los límites pueden agregar `retryAfter` y el encabezado `Retry-After`.

### Cobertura HTTP agregada en esta Tarea 0

`Contracts/WhatsAppRouteContractsTests.cs` comprueba las cuatro combinaciones condicionales en `EndpointDataSource` y por HTTP para los tres estados válidos. También fija `405` `Http.MethodNotAllowed` si se usa otro verbo mientras la ruta existe frente a `404` `Http.NotFound` cuando se omite, ambos con `traceId`. Con WhatsApp apagado, confirma que siguen registradas las dos rutas de login link, `GET /account/login-methods`, `PUT+DELETE /api/me/whatsapp` y las rutas compartidas `POST /account/login-code/verify` y `GET /api/me`. Comprueba `400` de confirmación sin código vigente y `204` de desvinculación autenticada.

`Contracts/WhatsAppHttpContractsTests.cs` agrega `415` `Request.Invalid` para un pedido de código con otro Content-Type; `400` `Request.Invalid` para JSON inválido o ausente en ambos pedidos de código; `200` vacío para webhook firmado con cuerpo JSON inválido o vacío; persistencia de un mensaje recibido en bytes firmados con `Content-Type: text/plain`; y el límite por IP compartido entre GET y POST del webhook. Los errores nuevos se comprueban con `code` y `traceId`. El lector actual descarta un webhook firmado ilegible y responde `200` para evitar reintentos indefinidos de Meta.

El prototipo con acciones MVC y `IActionDescriptorCollectionProvider` queda pendiente para el integrador: este encargo fija el contrato del código actual y recomienda el mecanismo, sin registrar controllers todavía.

## Estados de configuración al arrancar

`WhatsAppRegistration.AddWhatsApp` calcula y registra una sola instancia de `IWhatsAppAvailability` (`src/ArquitecturaBase.Infrastructure/WhatsApp/WhatsAppRegistration.cs:28-38`). Los flags se evalúan al mapear las rutas, no por pedido.

| Estado válido | Configuración | `IsEnabled` / `IsWebhookEnabled` | Combinaciones condicionales registradas | Rutas permanentes |
| --- | --- | --- | --- | --- |
| Apagado | `WhatsApp:PhoneNumberId` vacío o whitespace. | `false` / `false` | Ninguna. | Login methods, ambos login link, `PUT+DELETE /api/me/whatsapp` y rutas compartidas. |
| Envío sin webhook | `PhoneNumberId` y `AccessToken` presentes; `AppSecret` y `VerifyToken` ambos vacíos. | `true` / `false` | Los dos POST de solicitud de código. | Las mismas. |
| Envío y webhook | `PhoneNumberId`, `AccessToken`, `AppSecret` y `VerifyToken` presentes, con opciones válidas. | `true` / `true` | Ambos POST de código y `GET+POST /webhooks/whatsapp`. | Las mismas. |

Con `PhoneNumberId` presente y solo uno entre `AppSecret` y `VerifyToken`, la validación de opciones falla y la API **no arranca** (`WhatsAppOptionsValidator.cs:26-45`; `WhatsAppRegistrationTests.cs:131-147`). Si `PhoneNumberId` está vacío, WhatsApp permanece apagado aunque esos secretos tengan algún valor. El webhook encendido exige además `Authentication:Issuer` válido (`WhatsAppRegistration.cs:120-123`; `WhatsAppRegistrationTests.cs:149-179`). El estado inválido no tiene contrato de rutas que medir.

## Viabilidad del registro condicional en MVC

La vía concreta es una `IApplicationModelConvention` registrada en `MvcOptions.Conventions`. Un atributo marcador en **cada acción condicional** indica si requiere `IsEnabled` o `IsWebhookEnabled`. En `Apply(ApplicationModel)`, la convención recorre `controller.Actions` en orden inverso y elimina con `RemoveAt` las acciones cuyo requisito no se cumple. `IWhatsAppAvailability` ya es singleton y expresa los flags calculados en startup. El registro previsto es `AddControllers()` más `AddOptions<MvcOptions>().Configure<IWhatsAppAvailability>((options, availability) => options.Conventions.Add(new ConditionalWhatsAppRoutesConvention(availability)))` en la composición de presentación; `MapControllers()` se agrega al enrutamiento durante la migración. La [documentación oficial de ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/mvc/controllers/application-model?view=aspnetcore-10.0) confirma que las convenciones se ejecutan al iniciar y permiten modificar el modelo de controllers y acciones; `ControllerModel.Actions` es una [colección modificable de acciones](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.mvc.applicationmodels.controllermodel.actions?view=aspnetcore-10.0).

Marcar únicamente `POST /account/login-code/whatsapp`, `POST /api/me/whatsapp/code` y las dos acciones del webhook. No marcar el controller completo de cuenta o perfil: eso eliminaría rutas permanentes. Quitar las acciones del modelo impide que nazcan sus `ActionDescriptor` y endpoints. Es más fuerte que ocultarlas de ApiExplorer, usar un filtro o devolver `404` desde una acción siempre registrada. Durante la transición, `MapControllers()` puede coexistir con `MapEndpoints()`; cada ruta heredada se retira cuando su controller alcance paridad para evitar un verbo/ruta duplicado.

El spike de viabilidad debe consultar `IActionDescriptorCollectionProvider.ActionDescriptors.Items.OfType<ControllerActionDescriptor>()` y la tabla de endpoints para afirmar método+ruta **presentes o ausentes** en los tres estados válidos. Las peticiones HTTP deben fijar `404` `Http.NotFound` cuando falta una ruta, éxito y errores cuando está presente, y permanencia de `PUT+DELETE /api/me/whatsapp` y login link cuando WhatsApp está apagado. Un `404` HTTP solo no demuestra que la ruta haya sido omitida: también podría producirlo una acción registrada.

Para el POST del webhook, el controller debe conservar la lectura de `Request.Body` como bytes antes de cualquier parsing o binding, validar HMAC sobre esos mismos bytes y mantener el límite de 5 MiB (`WhatsAppWebhookEndpoints.cs:78-103,141-190`). `[FromBody]` o un contrato JSON modelado por MVC introducirían respuestas de binding y podrían modificar la firma, el tratamiento de Content-Type y los status. El GET debe enlazar explícitamente los tres nombres `hub.*` de la query y devolver el challenge como `text/plain` literal.
